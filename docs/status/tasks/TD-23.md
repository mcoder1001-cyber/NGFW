Branch `task/TD-23` (worktree `/root/ngfw-wt/TD-23`), base `main@228a7c57`. Test infrastructure only — no
feature handlers, no product code. This is a merger request (D-134): four wave-A branches each add their own
`action` handler to `apps/api/src/testing/fake-agent.ts`, and three add their own hook line to
`apps/agent/internal/descriptors/core/coretest/fakevpp.go`; this task lands the seam mechanically so each

## What changed

### 1. `apps/api/src/testing/fake-agent.ts` — Action dispatch table

- `export type ActionKind = keyof ActionRequest` — the populated field of an `ActionRequest`
  (`'ping' | 'traceroute' | 'capture'` today; grows automatically as a later contract PR adds oneof cases).
- `export type ActionHandler = handleServerStreamingCall<ActionRequest, ActionOutput>` — a feature's
  handler for one kind, same shape as the RPC itself.
- `actionHandlers: Partial<Record<ActionKind, ActionHandler>>` (module-private) +
  `export function registerActionHandler(kind, fn)` — throws if `kind` is already registered (two
  features claiming the same case is a bug to resolve explicitly at rebase, not a silent replace).
- `export function resetActionHandlersForTest()` — test-only, undoes registration between cases.
- The `action` RPC inside `FakeAgent.impl()` is now a fixed dispatcher: it finds which field of
  `call.request` is set (`actionKindOf`), looks it up in `actionHandlers`, and:
  - no handler → ends the call with `UNIMPLEMENTED` via `call.emit('error', …)`;
  - handler throws → ends the call with the thrown error's own `code` or `INTERNAL`, same mechanism.
  - **Never `call.destroy()`** — confirmed by reading `@grpc/grpc-js`'s `ServerWritableStreamImpl`
    (`build/src/server-call.js`): the stream's own constructor installs an `'error'` listener that sets
    the pending status and calls `this.end()`; `destroy(err)` marks the stream destroyed *before* that
    listener's `end()` can run, so the status is never sent and the client hangs to its deadline — the
    exact bug F-nat44-ed-sessions found and fixed ad hoc in its own branch. `call.emit('error', …)`
    doesn't destroy the stream, so the listener's `end()` actually flushes the status.
- Both files carry the literal comment "features register here; never edit the dispatcher".

### 2. `apps/agent/internal/descriptors/core/coretest/fakevpp.go` — extension registry

- `RegisterExtension(name string, install func(*VPP))` — appends to a package-level ordered list;
  panics immediately on a duplicate `name` (copy-paste of the one-liner, not a second feature reusing it).
- `New()` now calls `v.installExtensions()` after `sanitizetest.Clean(...)`, which applies every
  registered extension in registration order (a no-op today: nothing has been rebased onto this seam yet).
- `VPP.On(name, h)` **shadows** the embedded `*fake.Client.On`, so every existing `v.On(...)` call inside
  any current or future `coretest/<slug>.go` extension file goes through it with **zero changes to that
  file** (Go method resolution: a method declared directly on `VPP` takes precedence over one promoted
  through the embedded `*fake.Client`). While an extension is installing (`installingExt` is set), it
  tracks which extension last claimed each VPP message name (`onOwner`); if a *different* extension then
  claims the same name, it panics naming both extensions and the message, instead of silently replacing
  the handler. Core setup (`install`, `installIfExt`, run before any extension) and an extension
  replacing its own earlier registration are unaffected — only two distinct extension names colliding
  panics.
- This is the real, load-bearing case, not a hypothetical: reading the actual wave-A branches (see
  below) shows **F-rpf-adl-pbr and F-bridge-l2 both hook `"feature_is_enabled"`** — uRPF/ADL's arc
  checks vs. the mactime feature's device-enable check — with completely different, mutually exclusive
  logic and no fallback to each other. Plain `fake.Client.On` (which replaces unconditionally) would let
  whichever extension installs second silently discard the first's `feature_is_enabled` model the
  moment both land on main, breaking that feature's own tests for no visible reason. `VPP.On` turns that
  into an immediate, named panic instead, forcing an explicit fix at whichever rebase lands second
  (e.g. dispatching on `req.ArcName`/`req.FeatureName` in one shared handler) — TD-23 stops here
  deliberately: resolving that collision is feature code, out of scope for this task.
- Package doc / comment carries the literal "features register here; never edit the dispatcher" line.

### 3. Tests (new)

- `apps/api/src/testing/fake-agent-action.test.ts` — over a real gRPC connection (unix socket, exactly
  like `commit.service.test.ts`'s pattern): a registered handler runs and is observed on the wire;
  an unregistered kind answers with a real `UNIMPLEMENTED` status (not a hang); a handler that throws
  still ends the call with a status (`INTERNAL`, message preserved); `registerActionHandler` throws on
  a duplicate kind.
- `apps/agent/internal/descriptors/core/coretest/extensions_test.go` — `TestRegisterExtensionCompose`
  (two extensions hooking different messages both take effect via `New()`, verified via `Handles` and a
  round-trip `Invoke`); `TestOnExtensionCollisionPanics` (the exact F-rpf-adl-pbr × F-bridge-l2
  `feature_is_enabled` shape, reproduced with a lightweight `api.Message` test double — drives
  `installingExt` directly, white-box, so a deliberately-colliding pair never lands in the shared
  package-level registry and break every later `New()` in the test binary); the parallel-good case
  (`TestOnSameExtensionReplacesItsOwnRegistration` — an extension layering on core or on its own earlier
  registration must not panic); `TestRegisterExtensionDuplicatePanics`.

## Fix round 1 (review `85a7d12e`, `docs/status/tasks/TD-23-review.md`, verdict APPROVE WITH CHANGES)

Time-boxed 45 min. All six review items addressed:

- **F1 (the review's one blocking-before-merge item).** The F-bonding row in the registration table
  above was wrong: it described a direct `v.installBonding()` line, but the branch's actual current
  diff (re-checked fresh, tip `79a9ee1b`) shows it redeclares its own `var extensions []func(*VPP)` +
  loop — byte-identical to F-nat44-ed-sessions' hunk. Every one of the 7 rows was re-diffed fresh
  against each branch's current tip in this round (not carried over from the first pass) — branches on
  this shared host move under concurrent agents, so "checked once" doesn't mean "still true"; tips are
  now recorded per row so the next check has a baseline.
- **F2.** `fake-agent-action.test.ts`'s three (now four) `client.action(...)` calls that exercise a
  hang-detecting path all set `{ deadline: Date.now() + 2000 }`. A regression to `call.destroy()` now
  fails in ~2 s with `DEADLINE_EXCEEDED`, not Vitest's generic 30 s `testTimeout`.
- **F3.** The dispatcher's `try/catch` only ever caught a synchronous throw; `handler(call)`'s return
  value is now checked with `result instanceof Promise` and `.catch()`-handled the same way, so an
  `async` handler that rejects after an `await` also ends the call with a status. New test:
  "ends the call with a status when a handler rejects asynchronously, instead of hanging (F3)".
- **The `feature_is_enabled` clash (the review's F5).** Added `RegisterFeatureIsEnabled(featureName,
  fn)` in `fakevpp.go`: one `feature_is_enabled` handler, installed once by `install()` (core, before
  any extension — so registering through it never itself claims a VPP message name and so never trips
  `VPP.On`'s collision guard), keyed by `req.FeatureName`, falling back to VPP's own unknown-feature
  default (`IsEnabled: true`) for anything unregistered. New test `TestFeatureIsEnabledCompose`
  composes a stub of F-rpf-adl-pbr's real arc/feature model (`"adl-input"`, per-`SwIfIndex`) with a
  stub of F-bridge-l2's real index-only mactime model (`"mactime"`, also per-`SwIfIndex`, deliberately
  ignoring `ArcName` the way the real branch does) on the same `*VPP`, proving neither's answer bleeds
  into the other's, plus the unregistered-feature default; `TestRegisterFeatureIsEnabledDuplicatePanics`
  mirrors the extension registry's duplicate guard. **The registration-line table above now gives both
  F-rpf-adl-pbr and F-bridge-l2 their exact lines through this seam** — whichever rebases second no
  longer trips `VPP.On`'s panic for `feature_is_enabled` at all; it composes.
- **F4/F6.** Documented the "no reset, package-level global" convention in both README comments: the
  TS side (`fake-agent.ts`, near `actionHandlers`) tells every test file that registers a handler to
  call `resetActionHandlersForTest()` in its own `afterEach`, same as this task's own test does; the Go
  side (`fakevpp.go`, near `RegisterExtension`) says the same for `RegisterExtension` and
  `RegisterFeatureIsEnabled` — no Go-side reset exists, a registered name is permanent for the test
  binary's life, fine for a real feature's `init()` or a test-only name nothing else queries, never a
  real feature's slug/FeatureName reused from a test.
