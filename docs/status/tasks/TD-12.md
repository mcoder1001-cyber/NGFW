# TD-12 — de-flake load-sensitive tests that break merge gates

Scope: **test code only** (apps/agent Go tests + apps/api/apps/web vitest configs). No product code touched.

## What was built

Five load-sensitive test patterns were investigated (the four named in the envelope + a grep for
others on the scheduler/service/stream paths). Three were races against a real background
timer/goroutine that a fixed sleep tried to "outlast"; one was vitest's own worker pool timing out
under CPU contention. Each is fixed by waiting on the actual condition (bounded) or removing the
wall-clock dependency entirely, never by just enlarging a sleep.

### 1. `apps/agent/internal/agent/service_test.go::TestGRPCRoundTrip`

**Root cause**: `grpc-go`'s client-side `StreamEvents` call can return before the server's handler
goroutine has run far enough to call `bus.subscribe`. A fixed `time.Sleep(50ms)` assumed that was
always enough; under host load the server goroutine can be scheduled later than that.

**Fix**: added `waitForSubscriber(t, s)` — polls `s.bus.subs` (same-package unexported field) until
non-empty, bounded at 10 s, `t.Fatal`s if the bound is exceeded (a real regression still fails fast
instead of hanging silently).

**Repro (before fix)**: temporarily set the sleep to `0` and ran under the host's current real load
(other workers' CI, `uptime` load average ~17–26 at the time) — reliably reproduced:

```
$ go test ./internal/agent/... -run 'TestGRPCRoundTrip' -count=60
--- FAIL: TestGRPCRoundTrip (10.48s)
--- FAIL: TestGRPCRoundTrip (0.12s)
--- FAIL: TestGRPCRoundTrip (10.02s)
--- FAIL: TestGRPCRoundTrip (0.02s)
... (24 of 60 runs failed)
FAIL	ngfw/agent/internal/agent	70.490s
```

**After fix**, same command shape, real load average 13.9–26.1 at run time:

```
$ go test ./internal/agent/... -run 'TestGRPCRoundTrip|TestPendingSurvivesRestartAndRevertsAfterDeadline' -count=60 -v
... 120/120 --- PASS ...
ok  	ngfw/agent/internal/agent	24.608s
```

### 2. `apps/agent/internal/agent/service_test.go::TestPendingSurvivesRestartAndRevertsAfterDeadline`

**Root cause**: `ConfirmTimeoutSec: 1` arms a *real* `time.AfterFunc` deadline timer
(`armTimerLocked`). The test called `apply()` then immediately `s.Close()`, assuming that gap is
always < 1 s. Under host load the goroutine between those two lines can be descheduled long enough
for the real timer to fire and revert-and-persist *before* `Close()` stops it, so the restarted
agent loads state with the pending txn already gone — `"pending txn not persisted"`. Baseline runs
already showed the margin eroding under real (moderate) load: `confirm timer armed ... in=558ms`
against a nominal 1000ms budget (i.e. ~44% already eaten by scheduling before the test even reaches
`Close()`).

**Fix**: removed the wall-clock race entirely. `ConfirmTimeoutSec` is now 3600s (the real timer
cannot plausibly fire during test setup), and the "deadline already passed" precondition needed by
the restart+resync assertions is created directly on disk (`loadState` + backdate
`meta.ConfirmDeadline` + `save()`) instead of sleeping past a real one. No `time.Sleep` remains in
this test.

**Repro (before fix)**: kept `ConfirmTimeoutSec: 1`, inserted a `time.Sleep(1200ms)` between
`apply()` returning and `Close()` (this is exactly what host load does to that gap):

```
$ go test ./internal/agent/... -run TestPendingSurvivesRestartAndRevertsAfterDeadline -v
    service_test.go:413: pending txn not persisted
--- FAIL: TestPendingSurvivesRestartAndRevertsAfterDeadline (2.34s)
```

**After fix**: 60/60 pass (see combined run above); test now runs in ~0.01–0.35s (no sleep at all,
down from a fixed ~1.1–1.6s before).

### 3. `apps/agent/internal/renderers/strongswan/review_fixes_test.go::TestWatchResync`

**Root cause**: the fake charon's `push` is non-blocking and silently drops events when nobody has
subscribed yet (matches real govici). The test waited up to 2 s for `Watch`'s goroutine to
subscribe, but **did not fail** if that wait was exhausted — it just floods 400 events anyway. If
`Watch` hasn't subscribed within that window under load, all 400 events are dropped forever and the
overflow-triggered `KindResync` event can never fire, so the test hangs to its `ctx` deadline and
fails with `resync <bool> poll <bool>`.

**Fix**: widened the subscription wait to 15 s and the overall `ctx` to 45 s (generous margin over
the 300 ms resync interval used in this test), and made the wait **fail loudly** if exhausted
(`t.Fatal("Watch never subscribed")`) instead of silently continuing.

**Repro (before fix)**: temporarily skipped the subscriber wait entirely (`for i := 0; i < 0; i++`)
to simulate a `Watch` goroutine that hasn't been scheduled yet — reproduced the exact failure mode:

```
$ go test ./internal/renderers/strongswan/... -run TestWatchResync -v -count=5
    review_fixes_test.go:275: resync false poll false
--- FAIL: TestWatchResync (3.20s)
```

**After fix**:

```
$ go test ./internal/renderers/strongswan/... -run TestWatchResync -v -count=20
... 20/20 --- PASS ... (0.01–0.03s each)
ok  	ngfw/agent/internal/renderers/strongswan	0.361s
```

### 4. apps/api / apps/web vitest configs (config only)

**Root cause found**: reproduced the literal CI message on this host under real load (`uptime`
~14–30 at the time):

```
FAIL  src/commit/commit.service.test.ts [ src/commit/commit.service.test.ts ]
Error: [vitest-worker]: Timeout calling "fetch" with "["/src/commit/commit.service.ts","ssr"]"
```

This is **not** `test.testTimeout`/`hookTimeout` — it's vitest's own worker-pool RPC (the fork
asking the main thread to transform a module), whose timeout is `birpc`'s hardcoded
`DEFAULT_TIMEOUT = 60000` and is not exposed as a `test.*` option in the installed vitest (3.2.7;
checked the shipped `node_modules/.../vitest/dist/chunks/*.js` directly — no config path reaches
that `timeout`). Vitest's own default worker count is `cpus - 1`; with up to 12 worker slots on this
host each spawning that many forks for two projects (api + web), the resulting process count vastly
oversubscribes the host's 32 cores, so an individual fork's transform call can be starved past 60 s.

**Fix (config only, both files)**:
- `apps/api/vitest.config.ts`: added `testTimeout`/`hookTimeout`/`teardownTimeout: 30_000` (was
  vitest's default 5 s/10 s/10 s) and `maxWorkers: 4` to bound fork count.
- `apps/web/vite.config.ts`: added `teardownTimeout: 30_000` (testTimeout/hookTimeout were already
  30 s) and `maxWorkers: 4`.

**After fix**, apps/api unit suite run 3 times back-to-back under real load (~19–38):

```
Test Files  10 passed (10)   Tests  96 passed (96)   Duration  17.86s   (load 19.24/38.31/32.63)
Test Files  10 passed (10)   Tests  96 passed (96)   Duration  36.21s
Test Files  10 passed (10)   Tests  96 passed (96)   Duration  25.79s
```

No further `Timeout calling` errors observed after the change, across all runs.

### 5. Grep for other time.Sleep-then-assert / fixed timeouts (scheduler/service/stream paths)

Findings, everything **not** fixed and why:

- `apps/agent/internal/renderers/strongswan/apply_test.go::TestWatchReconnectsAndPolls` has the same
  `waitSubscribed` shape (200×10ms = 2s bound) as #3 above, plus a
  `time.Sleep(1500ms) // at least one poll snapshot without the SA` ordering assumption. Same
  underlying risk class, **not fixed**: `apply_test.go` is outside this task's "files you own" list
  (only `review_fixes_test.go` is named) — left for a follow-up task/questions file rather than
  edited speculatively on a shared worktree.
- `TestRevertOwedWhenVPPDownAtDeadline`, `TestNewApplySupersedesOwedRevert`,
  `TestOwedRevertRetriedByTimer`, and the shared `revertObstacle` helper (all in
  `service_test.go`) use `ConfirmTimeoutSec: 1` too, but they **wait for the real timer to fire** via
  a bounded poll (`for cond && time.Now().Before(deadline) { time.Sleep(20ms) }`, 3–5 s bounds) —
  already the correct pattern from this task's brief. Not touched.
- `TestLateConfirmRejectedAfterRestart` (`service_test.go`) has the identical
  apply→`Close()`→`time.Sleep(1100ms)`→restart shape as #2, but reviewed line-by-line: `time.Sleep`
  guarantees *at least* the requested wall-clock time regardless of scheduling delay, and the
  post-restart assertions (`FailedPrecondition` either way; final `Resync` + interface-gone check)
  are satisfied whether the real timer reverted before or after `Close()`. Confirmed not
  load-flaky; left unchanged.
- `chrony/chrony_test.go` and `unbound/unbound_test.go`'s `time.Sleep(30ms) // process start times
  have 10 ms resolution` are sleep-*before*-acting (guaranteeing a clock-resolution gap), not
  sleep-then-assert-a-deadline; not a load-flake risk.
- `apps/api/src/**/*.test.ts` and `apps/web/src/**/*.test.ts(x)` (the quick-gate unit suites): no
  `time.Sleep`/`setTimeout`-based wait patterns found at all.
- `apps/agent/internal/scheduler/*_test.go`: no `time.Sleep` usage.
- All other `time.Sleep` hits are in `*_integration_test.go` files, gated behind
  `VRX_INTEGRATION=1` and `t.Skip` otherwise (never run on the quick merge gate) — out of scope by
  design (docs/00-MASTER-PROMPT.md FAST MODE rules).
