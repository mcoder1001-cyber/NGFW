# TD-17 — apply-startup product mode: installed paths, appliance approval gate, lab gate kept as a mode

Branch `claude/modest-keller-upaw4m` (cloud session), base `origin/main`. No lab slot and no appliance: the fake-host
harness is the only proof run here.

## Problem

Review 2026-09-24 item 6.4 (3), D-125. `deploy/vpp/apply-startup.sh` only worked from the manager's checkout: the
binaries were `/root/ngfw/apps/agent/bin/*`, and the gate read `docs/lab/host-<vm>.md` plus
`docs/decisions/PENDING-*.md` / `LOG.md` on main of `/root/ngfw`. None of that exists on an appliance, so P10 had to
ship the script disabled.

## What changed (`deploy/vpp/apply-startup.sh`)

- **`--mode lab|product`** (env `NGFW_APPLY_MODE`, default `lab`). It is recorded in the work dir settings and passed
  to the run, holder and dead-man units as `--setenv`, so the run recomputes the same gate.
- **Lab mode is unchanged.** It still uses the checkout binaries, the handover flag and the PENDING + D-row approval.
- **Product mode:**
  - The binaries default to `/usr/lib/ngfw/bin/ngfw-startupgen` and `ngfw-vppcheck`. `NGFW_LIB_BIN` changes the
    directory, and `NGFW_STARTUPGEN`/`NGFW_VPPCHECK` still override each binary.
  - It reads no docs/lab, PENDING or LOG file and does not need the canonical repo (`canon_root` and `GATE_REPO` are
    skipped).
  - **Appliance approval gate:** `--apply` needs `--approve-rendering <sha256>` equal to `--expect-new-sha256`, so the
    approval covers exactly one rendering, and `--expect-sha256` still binds it to the live file.
  - The dead-man timer is still mandatory: if it cannot be armed, the apply is refused. The locks, health checks and
    the single rollback are the same as in lab mode.
  - The gate record is `gate: product mode — appliance approval of rendering <sum> (dead-man mandatory)`.
- **Cross-mode flags are usage errors (exit 2):** `--approve-rendering` in lab mode, and
  `--i-have-product-owner-approval` in product mode.
- The dry run shows "appliance approval gate" in product mode and exits 3 when the approval is missing or wrong.

## Tests (`deploy/vpp/test-apply-startup.sh`, scenario 44)

- The cross-mode flags and an unknown `--mode` are refused.
- A missing installed binary is reported under `NGFW_LIB_BIN`.
- The fixture canonical repo is moved away for the product runs. They pass anyway, which shows they read no
  docs/lab or PENDING file.
- The dry run exits 3 without the approval and 0 with it, and nothing is changed.
- An approval of another sum is refused with no work dir.
- The product apply commits. The gate, the mode and the installed binary paths are recorded and pinned in the work
  dir. The dead-man is armed with `NGFW_APPLY_MODE=product` and cancelled after the commit. The locks are released and
  VPP restarts once.
- If the dead-man timer cannot be armed, the apply is refused (exit 3) and VPP is not restarted.
