# TD-13: scheduler tier-3 Validator and VPP→daemon stage (audit ARCH-02, D-125)

Branch `task/TD-13`, base `main@4f472cc7`. No host or VPP runs: unit tests use fake descriptors and the fake VPP.
No proto or contract change: the new finding uses `ValidationIssue.rule`, which is a free string.

## Summary

- **Validator.** `scheduler.Validator` is an optional descriptor extension:
  `Validate(ctx, key Key, value proto.Message, view ReadOnlyView) error`.
  - When it runs: in `Scheduler.Plan` (the DryRun RPC) and in every Apply, resync and revert. The scheduler calls it
    for every Create and Update of that descriptor, after planning and **before the first operation**, deletes
    included.
  - What a rejection does: it becomes a plan `Issue` (`CodeInvalid`, `Rule "agent.validator"`, plus the pointer the
    validator named with `InvalidAt`). DryRun reports it with `ok = false`. Apply answers **FAILED** with nothing
    touched. The fake VPP proves zero write calls.
- **Bounds.** Each call runs on its own goroutine under a 30 s deadline (`DefaultValidateTimeout`;
  `Scheduler.ValidateTimeout`). A validator that ignores ctx is abandoned. A panic is recovered, and each case is a
  finding.
- **Copies.** The value and the view are copies: nothing a validator does can change what is applied.
- **Redaction.** Finding text passes through `RedactLeaves`, which masks secret-named leaves and D-051 references as
  whole tokens. It is capped at 2 KiB.
- **Stage.** `scheduler.Stager` is optional: `StageVPP` is the default, `StageDaemon` the other value. The stage
  breaks topological ties **before** the registration order. A real dependency always wins. VPP creates and updates
  run before daemon ones, and deletes run the other way round. The rollback is unchanged (the exact reverse of the
  journal).
- **DryRun.** `report()` in `service.go` uses the finding's rule and pointer. When the finding has no pointer, it
  uses the object's own pointer.
- **Example adopter.** `fakeDaemon` in `scheduler/validator_test.go` (tests only). It was also checked against the
  real Kea descriptor of `task/F-kea-dhcp-relay` in a scratch tree (§4). Adoption takes two methods, `Stage()` and
  `Validate`, and nothing else.

## 5. Adoption recipe, one line per daemon feature (also in `docs/agent/scheduler-validators.md`)

Rule: *a daemon descriptor implements Validator and declares StageDaemon*. Add `Stage() scheduler.Stage { return
scheduler.StageDaemon }` and a `Validate` that renders and then calls the renderer's staged checker. Nothing else
changes.
- **F-kea-dhcp-relay** (`kea.dhcp4/vrx`, `kea.dhcp6/vrx`): `RenderFamily(value.(*DesiredState), d.family)` →
  `r.Validate` (`kea-dhcp<N> -t <staged>`, under `ip netns exec` on a slot).
- **F-unbound-chrony-syslog** (`unbound.config/vrx`; chrony and rsyslog alike): `r.Render(ctx, value)` → `r.Validate`
  (`unbound-checkconf`, `chronyd -p -f`, `rsyslogd -N1 -f`, each on the staged copy). Never the `prepare` hook.
- **F-host-acl-nftables** (`host-acl.nftables/vrx`): `r.Render(ctx, value.(*HostTable))` → `r.Validate`
  (`nft -c -f <staged>`). Never the store. Hold the descriptor mutex no longer than the render needs.
- **P12 (FRR)**: `r.Render(ctx, doc)` → `r.Validate` (`vtysh -C -f <staged>`). If several objects build one
  `frr.conf`, render it from `view.List(...)`. `frr-reload.py --test` is only for a diff.
- **P11 (strongSwan)**: `r.Render(ctx, doc)` → `r.Validate`
  (`swanctl --load-all --noprompt --file <staged> --uri <scratch charon>`). Only the scratch charon is loaded, with
  start_action set to none. PSKs are masked by the renderer's `toolMessage`.
- **F-snmp**: `r.Render` → `r.Validate` (`snmpd -C -c <staged check copy>`). The check instance lives in the staging
  dir and is stopped by its PID. The community is masked by the renderer and by the scheduler.

## 7. Decisions made here (the D-entry covers them)

- **Key type.** The key parameter has type `scheduler.Key`, not `string`. Every descriptor method uses `Key`, and it
  is a string type.
- **The view.** It is the plan's "after" set (desired plus kept actual), because Create receives only a value, so
  there was no existing view to name it after. It is named `ReadOnlyView`, as in the envelope.
- **Validation runs once per Apply, inside `plan()`.** That puts it after planning and before any operation, which
  also means before the first Create. Q1 explains why there is no second run.
- **Findings reuse the existing plan-issue path.** That path is ApplyWith's FAILED, DryRun's report, and TD-8's
  dynamic-source culprit, which leaves out a source whose object a validator rejects. So no new outcome and no proto
  field.
- **A timeout is a finding; a cancelled transaction is an error.**
- **`Scheduler.ValidateTimeout` semantics.** 0 means the default and a negative value means no own bound. This is
  deliberate: `New()` is left untouched, so there is no conflict with TD-9's `New()` hunk.
