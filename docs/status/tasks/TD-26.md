# TD-26 — Core VRF tolerant delete: a table VPP keeps locked is left, recorded and warned

Branch `claude/modest-keller-upaw4m` (cloud session), base `origin/main`. No lab slot: the host proof is not run here.

## Problem

F-nat44-ei-64-66-nptv6 review H1/H2 (V-new (c)). VPP 26.06 nat64 locks a tenant VRF's IPv6 table on every prefix add
and static-BIB add/delete and never unlocks it (`nat64.c:864-866`, `1207-1224`). `ip_table_add_del(del)` removes only
the API lock (`fib_table_lock_clear`), so the table survives, still named `<owner>:<vrf>`, until VPP restarts. The VRF
Retrieve kept reporting `vrf/<id>`, verify failed with "vrf/<id> still present", and the whole transaction was rolled
back (DEGRADED when a revert failed) — on every commit, rollback, confirm-revert and resync that deletes the VRF.

## What changed (`apps/agent/internal/descriptors/core/vrf.go`)

- **Delete** re-reads the table after the delete. Families still named `<owner>:<vrf>` are recorded as "deleted by us,
  kept alive by VPP", bound to the VPP boot identity (D-080, `bootid.Current`), and a `slog.Warn` names the table.
  The delete succeeds.
- **Retrieve** hides recorded families while the boot identity matches; a record of another boot is expired (the
  table is then reported again and handled normally).
- **Create/Update** of the same VRF re-asserts the table (a new API lock, as before) and drops the record.
- Records are in memory, keyed by VPP client + owner + table id (the descriptor value carries only `Env`, registered
  by `core.go`, not this task's file). An agent restart forgets them; the next resync plans the delete again and
  records them again.
- A recreate under a **different** VRF name on a kept id still fails with `ErrTableConflict` (VPP cannot rename a
  table) — correct and visible.

## Tests

- `TestVRFDeleteKeptLockedByVPP` (`vrf_kept_test.go`, core fake VPP with an ip_table_add_del handler that keeps a
  locked IPv6 family): the delete applies, IPv4 is gone and IPv6 left, Retrieve hides it, an empty resync plans
  nothing, a recreate reports the full VRF again, and a boot-identity change (`bootid.SetProcRoot`) reports the kept
  table again. Without the fix it fails with `ROLLED_BACK … vrf/4064 still present`.
