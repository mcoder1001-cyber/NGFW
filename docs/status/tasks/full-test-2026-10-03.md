# اجرای تست‌های باقی‌مانده — ۲۰۲۶-۱۰-۰۳

این اجرا به دستور صریح کاربر برای انجام همهٔ تست‌های باقی‌مانده انجام شد. نتیجهٔ کلی سبز نیست: مجموعه‌های واحد، integration، توپولوژی، قابلیت‌های opt-in و مسیر NIC اجرا شدند؛ شکست‌های واقعی، نقص fixture، SKIP و سناریوهای هنوز پیاده‌سازی‌نشده جدا ثبت شده‌اند. هیچ ردیف برنامه صرفاً با یک smoke تکمیل اعلام نشد. تست‌ها مستقیماً اجرا شدند؛ نشانگر `plan/NO-TESTS` حذف نشد و gate compile-only به‌عنوان اجرای تست گزارش نشده است.

## شبکه و قابلیت‌هایی که واقعاً بررسی شدند

- مسیر دو کارت ens193 و ens256 با af_packet و سپس DPDK VMXNET3، دو queue و دو worker: در هر اجرا 100/100 ICMP پس از warm-up در هر جهت، 10/10 DF/1500 در هر جهت و TCP exact echo برابر 10 MiB موفق. [گزارش سخت‌افزار](hardware-2026-10-03.md).
- NICها کارت مجازی VMware هستند؛ این نتیجه passthrough کارت فیزیکی یا throughput ظرفیت خط نیست. DPDK فقط در VPP مجزا اجرا شد؛ VFIO no-IOMMU موقت بود و مقدار enable_unsafe_noiommu_mode به N و درایور NIC به vmxnet3 برگشت.
- smoke، توپولوژی interfaces، QoS و system identity موفق؛ bridge-L2 پس از افزودن محدودهٔ ID به fixture موفق؛ NAT44-ED sessions و NAT44-EI/64/66/NPTv6 نیز پس از همین تنظیم fixture موفق.
- NAT46 return-path: ICMP و TCP واقعی از IPv4 client به IPv6 server، مسیر برگشت و افزایش شمارندهٔ MAP موفق؛ اشیای تست پاک شدند. API nat46 E2E همچنان یک شکست validation مستقل دارد.
- WireGuard handshake واقعی در Go موفق. driver سرتاسری API/Web اجرا شد ولی commit با 403 licence.feature.wireguard رد شد؛ آن driver موفق محسوب نمی‌شود. کلید خصوصی در شواهد ذخیره نشده است.
- SRv6 و MPLS globals، VRRP، DNS، GTP-U، L2TP، LISP، DET44، PPPoE control-plane، IKEv2، DHCP، LCP، IPFIX، sFlow، flowprobe، PCAP، NSIM و stock strongSwan اجرا شدند. خروجی دقیق و skipهای داخلی هر مورد در index موجود است.
- VRRP driver: اعمال دو VR، idempotency، رد VRID تکراری، بازیابی پس از حذف اشیا، failover peer در namespace، keepalived و rollback اجرا شدند؛ طولانی‌ترین outage ثبت‌شده 0.0s در برابر حد 3s. driver در بخش نمایش state یک خطای jq داشت؛ exit=0 به‌تنهایی به معنی بی‌نقص بودن همهٔ مراحل نیست. این آزمون جایگزین HA دو VM نیست.
- RX worker placement و policer bind_to_worker روی VPP اختصاصی دو-worker موفق. تست restartSimulation در همان مجموعه به‌علت اختلاف RX placement/idempotency شکست خورد.
- metrics واقعی با rig: rx_bytes از 426 به 1028 رسید و از /metrics خوانده شد.
- auto-SDL ابتدا به‌علت session SDL غیرفعال skip شد؛ روی VPP مجزا با session enable rt-backend sdl تکرار و موفق شد. hoststack با rule-table فعال هم در session_rule_add_del خطای VPP داد و موفق نیست.
- تست scheduler با VRX_PERF=1، شامل حد wall-clock برای 20k object، و گزارش scale object store با 1000/2000/4000 object موفق.
- ACL counters، janitor، 100k rule خام در VPP، CSV dry-run/import و صفحه‌بندی اجرا شدند. commit 100k rule با RESOURCE_EXHAUSTED رد شد: پیام 9,928,995 بایت در برابر حد gRPC برابر 4,194,304. PASS سناریوی scale به معنی اعمال موفق 100k rule نیست.
- SRv6 stack driver موفق است ولی طبق خود driver بستهٔ SRv6 ارسال نمی‌کند؛ شواهد کنترل، state، restart agent و rollback است.

## شکست‌ها و علت‌هایی که پیدا شدند

1. L2TP cookieها در رفت‌وبرگشت JSON/protobuf به عدد/رشتهٔ متفاوت تبدیل می‌شوند؛ proto و TestProjectSchemaExamples شکست می‌خورند.
2. fixture SeedService برای default-vpp-nics به‌روز نیست؛ tunnel mapهای جدید با golden فرق دارند. web App.test.tsx نیز انتظار navigation قدیمی دارد.
3. coretest handler برای ip_mroute_add_del ندارد؛ TestP12ProjectionWithoutFRR شکست می‌خورد. TestMetricsCollectors انتظار صفر collector دارد ولی dashboard collector ثبت می‌شود.
4. drift پس از commit/rollback شامل حذف defaultهای management، nat، services و vpn می‌شود؛ API integration و تست زندهٔ reachability آن را تأیید کردند.
5. چند fixture قدیمی agent را با env پاک‌شده و بدون VRX_VPP_TABLE_BASE یا ID_RANGE اجرا می‌کنند. این موارد روی VPP اختصاصی با wrapper محدود به محیط disposable تکرار شدند؛ نتیجهٔ rerun جای نتیجهٔ اولیه را پنهان نکرده است. در برخی سناریوها پس از restart، API همچنان به socket پیشین وصل می‌شود و GET drift با 503/ENOENT شکست می‌خورد؛ bonding، host ACL و neighbors نمونه‌اند.
6. مجموعهٔ opt-in: LB garbage collection، IGMP، proxy-ND و DAD شکست داشتند. DET44/MAP/CNAT packet topology، Kea commit و unbound/chrony/syslog نیز خروجی شکست دارند. متن دقیق assertion/API error در test-summary.json است.
7. BGP/OSPF/FRR ابتدا به‌علت دسترسی frr به /run/vrx-test (0700) متوقف شدند. rerun با bind mount خصوصی و directory قابل traversal انجام شد؛ permission میزبان عوض نشد. نتایج نهایی در گزارش تکمیلی پایین ثبت می‌شود.
8. MPLS descriptor ابتدا table 0 نداشت؛ rerun با table 0 فقط در VPP مجزا انجام شد. نبود این پیش‌نیاز با شکست عملکرد نهایی یکی محسوب نمی‌شود.

## اجرای مجدد و محافظت از میزبان

`run.py [--dpdk]` برای NIC smoke؛ `remaining-tests.py unit-modules|topology|opt-in|extra|topology-retry|acl-extra` برای مجموعه‌ها؛ `VRX_TEST_SLOT=<n>` برای انتخاب slot. `isolated-vpp.py <command...>` با private mount namespace یک VPP disposable را روی /run/vpp برای همان فرآیند قرار می‌دهد. `VRX_ISOLATED_TEST_RUN=1` runtime خصوصی برای daemonهای FRR و `VRX_ISOLATED_WORKERS=2` دو worker ایجاد می‌کند. `agent-isolated-wrapper.sh` فقط با startup.conf مربوط به bind mount خصوصی VPP، owner آزمایشگاهی و مسیرهای صریح تست اجرا می‌شود. فرمان سنگین با tools/heavy.sh اجرا می‌شود؛ timeout فقط process group همان تست را متوقف می‌کند.

تغییرات این کار شامل driverهای تست و گزارش است؛ feature محصول برای سبز کردن نتیجه تغییر نکرد. هیچ commit/push انجام نشده است. secret scan شواهد بدون leak گذشت؛ DSNهای لاگ حذف شده‌اند. بررسی نهایی سرویس، NICها، مسیر مدیریت و پاک‌سازی در بخش تکمیلی ثبت می‌شود.

## نتیجهٔ rerunها و بررسی نهایی

- FRR در runtime خصوصی: 161 نتیجهٔ Go موفق، صفر شکست؛ شامل renderer، description/secret/convergence checks، 10,240 static routes، BGP و OSPF زنده.
- OSPF و BGP توپولوژی با FIB proof روی VPP اختصاصی: هر دو PASS؛ یادگیری، policy filtering، withdrawal peer، restart agent و rollback بررسی شدند. خطای permission اولیه رفع پیش‌نیاز runtime بود و به خرابی protocol نسبت داده نمی‌شود.
- MPLS descriptor با MPLS table 0 در VPP اختصاصی: پنج نتیجهٔ موفق، صفر شکست.
- lint: 14/14؛ go vet agent: موفق؛ gen-check: موفق و generated paths تمیز؛ ci check و secret scan: موفق.
- بررسی wrapper با پارامتر نادرست `-version` (که agent آن را فرمان خروج نمی‌داند) agent را موقتاً با owner پیش‌فرض شروع کرد. PID همان فرآیند متوقف شد؛ چهار فایل تازه‌ساختهٔ agent-state.json، desired.pb، objects-fqdn-vrx.json و vpn-vrx.key و دایرکتوری‌های تازه و خالی آن پاک شدند. لاگ reconcile هیچ تغییر applied نشان نمی‌دهد و configهای سرویس میزبان تغییر نکردند. wrapper اکنون owner آزمایشگاهی، globals ownership خاموش و مسیر state/socket صریح را هم الزام می‌کند. این بررسی version test معتبر محسوب نشده است.
- VPP اصلی در پایان MainPID=1014، NRestarts=0؛ فقط local0، بدون LCP pair. همهٔ NICهای داده DOWN و دارای درایور vmxnet3؛ ens192 و default route via 172.30.126.1 حفظ شدند. VFIO no-IOMMU parameter برابر N است. ip netns list خالی و همهٔ VPPهای disposable این کار متوقف‌اند. interface پیش‌فرض kernel با نام ip6tnl0، بدون آدرس و DOWN، پس از بارگذاری tunnel support باقی است؛ ماژول‌های لازم آزمایش unload نشده‌اند.

همهٔ تست‌های runnable شناسایی‌شده اجرا یا تا محل شکست پیش‌نیاز/قابلیت امتحان شدند. شکست‌ها تعمیر محصول محسوب نمی‌شوند. موارد جدول «قابل تأیید نیستند» همچنان باز هستند و برای تأییدشان artifact، peer یا پیاده‌سازی لازم است.

مشاهدهٔ kernel پس از DPDK no-IOMMU: taint از 0 در بررسی اولیه به 64 رسید. این نشانگر با بازگرداندن VFIO parameter به N پاک نمی‌شود؛ میزبان reboot نشده است. مقدار و وضعیت نهایی در full-test-2026-10-03-evidence/final-host-state.txt ثبت شده است.
