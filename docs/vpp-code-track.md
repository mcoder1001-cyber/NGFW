# VPP code track — anything that would need C code inside VPP

Rule (00-CONTEXT FAST MODE): no C code in VPP during the 21-day plan. When a task hits a wall that
only VPP code would solve, the worker appends an entry here, implements the configuration-only
fallback, and says so in `docs/status/tasks/<id>.md`. The product owner decides later whether to
fund the item with a VPP engineer.

### V-new (F-qos-flat): qos mark survives an interface delete (V21/V23 family)

`vnet/qos/qos_mark.c` has no `VNET_SW_INTERFACE_ADD_DEL_FUNCTION` (unlike `qos_record.c:127` and `qos_store.c:140`, which
disable themselves on delete): `qos_mark_configs[source][sw_if_index]` keeps the egress map of a deleted interface while
the feature arc is cleared (`vnet_feature_add_del_sw_interface`). The next interface on that sw_if_index then (a) shows up
in `qos_mark_dump` as marking with that map, and (b) never gets the mark feature: `qos_mark_enable` (`qos_mark.c:82`)
enables the feature only when the config is `INDEX_INVALID`, so an enable on the reused index returns 0 and marks
nothing — silent, and invisible to a Retrieve. `policer_input/output` (policer plugin) have no delete hook either
(`policer_index_by_sw_if_index` stays), but their apply always re-enables the feature, and the agent never un-applies
without its own applied-once record (D-080), so only the mark is affected. Found reading the source (no crash path).
Fallback (configuration only): the agent removes marks before the interfaces they sit on (dependency order); the
interface sanitizer (TD-3 `ifsanitize.Acquire`) could send `qos_mark_enable_disable(enable=0)` for every source on a new
interface — proposed to the ifsanitize owner (F-qos-flat-questions.md Q7). Upstream fix: a delete hook in qos_mark.c that
calls `qos_mark_disable` for each source (0.5 day).

Second finding, same reading: **`policer_del` leaves interface bindings dangling.** `policer_input/output` bind an
interface to the policer's POOL INDEX (`policer_index_by_sw_if_index[dir][sw_if_index]`, `policer_op.c:220`), and
`policer_del` (`policer_op.c:62-86`) frees the pool entry without unbinding: the policer-input/-output node of that
interface then reads a freed (or later re-used) pool entry — a use-after-free on the packet path, or policing with
someone else's policer. The un-apply cannot be sent any more once the policer is gone (the by-name handler answers
NO_SUCH_ENTRY; `policer_input_v2` checks `pool_is_free_index`). Agent side (F-qos-flat): the scheduler always removes
attachments before their policer; the applied-once record of `policer.interface` also keeps the pool index it bound, so
a policer deleted and re-created behind the agent's back gets its attachments re-pointed (un-apply + apply, one
instance) on the next resync; a Delete after the policer vanished tolerates NO_SUCH_ENTRY. Upstream fix: `policer_del`
refuses (or unbinds) a policer that is still bound (0.5–1 day).

not reproduced on the shared VPP, no packets were sent). Every call that leaves a family unchecked hits it — e.g. the
