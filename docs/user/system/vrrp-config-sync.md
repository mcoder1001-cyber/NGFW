# High availability and configuration sync

Configure VRRP and cluster membership under **System → High availability**. Edits are staged in the candidate; commit or confirmed-commit applies them. Live role chips come from the owner's VPP runtime or the agent's keepalived instance, with current effective priority. Unavailable observations show Unknown. The native engine observes VPP transition events; keepalived uses its notify records and its bounded cached live dump.

For a two-node cluster, set a unique `ha.cluster.nodeName` on each node and reciprocal `peers` entries. Set each peer's `certificatePin` to the lowercase SHA256 hex digest of its HTTPS leaf certificate (DER bytes). Use the actual HTTPS listener port in `ha.cluster.port`; the existing trusted-proxy configuration must correctly identify the TLS terminator. Plain HTTP, an absent/mismatched pin and expired certificates are refused. Each node must provision the same cluster authentication key through the secret store (`key/<name>`, at least 32 bytes); only its reference enters configuration.

Ordinary commits and confirmed promotions automatically send the confirmed running document only when every enabled configured virtual router is observed as Master without an error. Missing, mixed Master/Backup, unknown or failed observations refuse automatic writer authority; disabled routers do not participate. A node with no enabled virtual router has no automatic writer authority. Multi-master configuration merging is out of scope. Pending commit windows never send speculative changes. **Force sync** sends the confirmed running document from the selected node, including when it is Backup; this explicit operator action chooses the authoritative sender. It refuses while another sync runs. Incoming deliveries use the ordinary schema/semantic/dry-run, agent apply and revision-promotion engine, with revision kind `cluster-sync`; those revisions never automatically relay back. Dirty or locked candidates, pending confirmations and degraded/reconciling running state refuse the delivery.

The fixed node-local exclusions preserve the entire cluster transport/membership settings, management credentials and TLS settings, hostname, setup, host and dataplane settings. Set additional JSON pointers in `ha.cluster.syncExclude` for node-specific interface addresses and other local settings. Each receiver enforces its own exclusions even if the sender fails to omit them. Array elements are replaced as part of their containing field; exclude the full address array rather than an individual index.

Secret values never leave the node. References remain in the replicated document; provision the corresponding references on the receiver first. A missing reference returns `cluster-missing-secrets` naming only references. Cluster requests bind origin, source revision, timestamp, nonce and document with HMAC SHA256; timestamps have a 30-second acceptance window and the bounded in-memory nonce cache prevents duplicate delivery during the window. The receiver also reads the last accepted source revision from durable revision provenance under the commit lock and refuses older or equal source revisions, including after API restart. If a sender restores a database with lower revision numbers, resynchronization requires deliberate administrator recovery; lower numbers never silently overwrite a newer replica. HTTPS certificate pins authenticate the destination before any request body or authentication header is sent.

The live cluster table reports each peer's last successful revision, observed role, source revision lag and error. This observation cache resets after API restart, displaying unknown until the next successful sync. It is not the configuration datastore; revisions remain durable in PostgreSQL. An unavailable peer records an error and can be retried with Force sync or the next confirmed local commit. Each peer request has an eight-second timeout, no redirect or HTTP fallback, bounded response size and shutdown cancellation.

REST equivalents: `GET /api/v1/state/ha/vrrp`, `GET /api/v1/state/ha/cluster`, `POST /api/v1/actions/ha/sync`. Edit `/api/v1/config/ha` and commit with the ordinary configuration endpoints. CLI users can use the generated generic configuration and API operations; no direct VPP command runs in the API.
