## What was built

### The fix: `apps/agent/internal/descriptors/core/ifaddr.go`, the Retrieve hunk plus two helpers

**The bug.** VPP's DHCPv4 client installs its lease with the ordinary interface-address call
(`dhcp_client_acquire_address` → `ip4_add_del_interface_address`, `plugins/dhcp/client.c:120-156`). So
`ip_address_dump` lists the lease next to our own addresses. `InterfaceAddrDescriptor.Retrieve` reported every
address of every tagged interface, so the lease counted as an undesired object of ours. The next reconcile or resync
deleted it with `sw_interface_add_del_address is_add=0`.

**The fix.**
- Retrieve now leaves out, per `sw_if_index`, exactly the installed lease that `dhcp_client_dump` reports:
  `lease.host_address/mask_width`. That is VPP's `client->installed` copy (`dhcp_api.c:246-274`).
- It is declarative, with no imperative workaround. The lease is VPP-owned state and never becomes an object of ours.
- **Bounded (D-132):**
  - one `dhcp_client_dump` per Retrieve, read lazily the first time an address of ours is seen;
  - no dump when there is no address of ours;
  - no new polling.
- **Fail-closed:**
  - A dump error fails the Retrieve, and with it the transaction. The lease is never classified by guessing.
  - An unknown message means the dhcp plugin is not loaded, so there can be no client and no lease; that is an empty
    set.
  - An unbound client has host address `0.0.0.0`, installed nothing, and excludes nothing.
- **Exact:**
  - Only the lease prefix is left out. A stray non-desired address of ours on the same DHCP interface is still deleted.
  - A lost static address is re-created, and a static that leaves the desired state is removed.
- **Architecture:**
  - Core reads the generated `binapi/dhcp` directly. The message name comes only from the bindings (rule 6).
  - Core does not import the DF-8 descriptor package, and `subsystems.go` does not change.
- The static IPv4 next to `dhcpClient` rule stays F-kea's schema rule (`interfaces.kea-dhcp-relay-dhcp-client-no-static`).
  It is reused, not duplicated (Q4).

### Tests: every new test fails on the base first (evidence below)

- **`core/dhcplease_test.go`, six tests.** They run core plus DF-1's alias on the coretest fake, with a tagged VLAN
  sub-interface `host-w7c0.100` holding the lease and a static IPv6, and a tagged LAN with a static IPv4. They cover:
  - Retrieve omits the lease, with one dump per Retrieve;
  - the Plan has no Delete;
  - one reconcile, two resyncs, and an agent restart with two resyncs keep the lease with zero address deletes;
  - statics are still reconciled: a stray is deleted, a lost static is re-created, and a removed IPv6 is deleted;
  - a renewal to another address, and an unbound client;
  - a failing dump fails the Retrieve with no delete, a missing plugin gives no leases, and there is no dump without
    addresses.
- **`internal/agent/dhcplease_test.go`, one test through the product wiring.** A DF-1 sub-interface on af_packet runs
  DF-8 `dhcp.client`, and a lease is bound on it. Then:
  - a re-apply is a no-op;
  - two `Service.Resync` calls, then a restarted Service with two more resyncs, all leave the lease installed;
  - Retrieve equals the canonical document, with no lease under `ipv4`, so there is no drift;
  - `InterfaceState` still shows the lease;
  - switching the sub-interface from DHCP to a static IPv4 equal to the old lease works in one commit, because deletes
    run first and VPP releases the lease.
- **`core/coretest/dhcp.go`.** A model of VPP's DHCPv4 client:

  - deleting a client releases the lease address.
  - The state lives on `Iface.DHCP`, so there is no package-level map (F-kea review L9).

**Setup.**
- The real `vrx-agent` of this tree, with owner `w7` and `VRX_VPP_TABLE_BASE=7000`. No API or DB is needed; the test
  drives the agent with `vrx-agentctl`.
- netns `ns-w7-dhcp`: veth `w7d0` ↔ `w7d1`, VLAN `w7d1.100` with 10.7.100.1/24, and a slot-local `dnsmasq`:
  - DHCP only, bound to `w7d1.100`;
  - pool .50–.59, lease time 10 min;
  - no router or DNS option, so VPP's client installs no default route;
  - own lease and pid files under `/run/vrx-test/w7/td24`, stopped by PID;
  - never the host's kea or dnsmasq units.
- The agent creates `host-w7d0` (af_packet) and `host-w7d0.100` in VRF `w7-td24` (table 7024), with `dhcpClient`
  (broadcast flag) and a static IPv6.

**Steps.**
1. Wait for BOUND (`dhcp_client_dump`).
2. Re-apply the same document.
3. Restart the agent twice. Each start runs a full resync from the stored desired state.
4. After every step, check that:
   - the lease is still in `ip_address_dump`;
   - the client is still BOUND on the same address;
   - the agent log never names `interface-ip/host-w7d0.100/<lease>`;
   - the agent's Retrieve never shows the lease.
5. Cleanup: remove `dhcpClient`, and check that VPP released the lease; set the veth down (D-101); apply the empty
   document; check that no `host-w7d0*` interface and no table 7024 are left.

**Safety.**
- NRestarts is checked before and after. It was 2 at 09:2x.
- The names do not collide with the P08 rig, so the test also runs beside it in `ci.sh full` (slot 12).
- No trace commands, no VPP restart. The test itself sends no classify message; only the agent's own D-095 sanitizer does, on the interfaces it creates.

## Decisions (for the LOG)

1. `interface-ip` Retrieve leaves out, per sw_if_index, the DHCPv4 lease that `dhcp_client_dump` reports as installed.
   - One dump per Retrieve, lazily.
   - A dump failure fails the Retrieve; an unknown message means no leases.
   - Core calls the generated `binapi/dhcp` directly instead of the reviewer's suggested `Env` hook fed from DF-8's
     `Leases()`. That needs no wiring change, and it is one dump instead of `Leases()`'s dump plus interface dump.
     Core still does not import the dhcp descriptor package.
2. The coretest DHCP model keeps its state on `Iface.DHCP`, with no package-level state.
3. The host proof lives in `test/topology/interfaces`, reusing P08's helpers. Its names (`ns-<p>-dhcp`, `<p>d0/<p>d1`,
   table `<N>024`) do not collide with the rig in `ci.sh full`. The DHCP server sends no router option, so nothing is
   added to the shared table 0.
