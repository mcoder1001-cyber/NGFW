## Context
- Host 172.30.110.211 (i7-12700T hybrid, 3× Intel X710 quad 10G, 5× I226-V) runs VPP 26.06 with the start-up file applied on 2026-10-14 (sha256 `889f9a6fea6c2ec0e29088d4a816441bfe8c349f6913c64e06e3e05eff0ccc32`): 9 workers on cpus 2-9,17 plus main core 16 = 10 VPP threads, but `num-tx-queues 8` on every port. Threads 8 and 9 therefore share TX queues 0 and 1 with main and `vpp_wk_0`. On the `0000:02:00.x` X710 (NVM 9.56) a TX queue used by two threads trips the i40e Malicious Driver Detection: the hardware disables the queue until the next VPP restart or port down/up, and VPP dropped **23 % of all forwarded packets** (5 MDD events logged 2026-10-19/20, the last one reproduced on purpose). Full evidence: `docs/status/tasks/machine-211-vpp-tuning-wip.md` (PR #251).
- A runtime-only remap (`set interface rx-placement` / `set interface tx-queue`) has been live since 2026-10-20 05:30 and removed the loss (0 `tx-error` growth on the six test ports). It does not survive a VPP restart, and the five dead TX queues on the four `02:00.x` ports (`02:00.0` q1, `02:00.1` q0+q1, `02:00.2` q1, `02:00.3` q1) stay unusable until one.
- The permanent fix is a new `dataplane` document, `docs/status/tasks/machine-211-vpp-tuning-dataplane.json` (PR #251): 7 workers on the P-cores 2,4,6,8,10,12,14 (one per physical core, no hyper-thread pairs, no E-core worker), main core 16, `rxQueues 7` / `txQueues 8` on the twelve X710 ports (8 TX queues = 8 threads: no X710 queue is shared), the five I226-V ports unchanged at 4/4 (hardware maximum: they keep sharing 2:1 as today; igc has no MDD), buffers and hugepages unchanged. Rendering sha256 **`92985d0c7065ede7dfc417db011c891b06f634ff1c126a25f1493b0ab47191b6`**, reproduced on 2026-10-20 with the generator of origin/main (5593e5ab2; command and output in `docs/status/tasks/apply-211-vpp-startup-20261020-wip.md`) and by the host's own dry run with the installed product generator (same sum).
- **What the restart costs.** On 211 `ngfw-agent.service` has `Requires=vpp.service` and `ngfw-api.service` has `Requires=ngfw-agent.service`, so the restart takes VPP, the agent and the API (web UI) down together. Forwarding resumes only after DPDK has started the 17 ports (15 GiB hugepages, 1 M buffers) and the restarted agent has re-applied the interfaces and the three xconnect pairs. The process restart alone measured ≈6 s on this host (2026-10-19, D-253); the 2026-10-14 apply took 24 s from the install to the first VPP API answer (`/var/lib/ngfw/startup-apply/20261014-151047-62477/log`, 15:10:52 → 15:11:16), before the agent resync. **Expect ≈25–35 s without forwarding and without the web UI/API**, then the tool's 10 s settle and 60 s health window during which nothing on the box may be reconfigured. Decision policy always-ask #6 (the owner's test rig) and #7 (restarting the VPP process).
- **Rollback is not free.** A failed health check makes one automatic rollback: the backup is reinstalled and VPP restarted again, a second outage of the same length; if that check fails too, the tool ends in `console-needed` (file restored, VPP not restarted again: someone at the console). After `COMMITTED` the tool cannot reinstall `backup.conf`: it only installs a rendering of a `--doc`. Going back means re-applying the 2026-10-14 document (`/var/lib/ngfw/startup-apply/20261014-151047-62477/doc.json`) through the same tool with an approval of its rendering (expected sum `889f9a6f…`): one more outage.
- **Never restart `ngfw-dataplane-performance.service`.** `vpp.service` has `Requires=ngfw-dataplane-performance.service` + `After=` (drop-in `/etc/systemd/system/vpp.service.d/40-resource-defaults.conf`, written on 2026-10-14) and `Requires=ngfw-hardware-211-bind.service` (drop-in `20-hardware-211-bind.conf`); an explicit restart of either propagates to VPP, the agent and the API (systemd.unit(5), the same mechanism as D-253/D-255). The new cores reach the governor by editing `/etc/ngfw/dataplane-performance.json` and running its `ExecStart` once (`/usr/local/libexec/ngfw-dataplane-performance`), before the apply; the oneshot stays active and `systemctl start` is a no-op.
- **The product's running configuration keeps the old document.** The apply installs a file rendered from a document file, not from a commit. The `dataplane` domain stored by the API on 211 (committed on 2026-10-14 through the installed `CommitService.systemCommit`, revision 2113) still says 9 workers / corelist 2-9,17 / 8 RX queues. Until it is changed through the API or the UI (System › Dataplane, then commit: that touches no VPP), `GET /api/v1/state/dataplane` and the UI preview show the installed file as different from running, and a future render *from running* would bring the 23 % loss back. Committing the new domain needs an administrator login (`ngfw configure merge dataplane …` + `commit`) and is a follow-up for the owner or an admin session, not part of this manager step.
- Host 211 is a product appliance (TD-17): there is no `/root/ngfw` checkout on it. The apply runs as `/usr/lib/ngfw/apply-startup.sh --mode product` (the installed copy is byte-identical to `deploy/vpp/apply-startup.sh` on main) with the installed binaries in `/usr/lib/ngfw/bin`, gated by `--approve-rendering <sha256>`; the lab-mode gate `--i-have-product-owner-approval PENDING-…` cannot be evaluated there.
