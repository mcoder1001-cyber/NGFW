## Source findings and historical comparison

Current `apps/agent/internal/descriptors/pppoe/client.go` adds negotiated IP addresses, a NORMAL FibPath on the physical interface and MSS clamp. It has no AC MAC/session-ID/encapsulation handle. The published IPv6 recovery adds family state/default-route lifecycle, not PPPoE framing. `pppoe.cp/global` is a separate globals-owner, write-only singleton; server sessions use the existing generated `PppoeAddDelSession` API. Current main lacks `subsystems/pppoe_native.go`, `test/topology/pppoe/` and the historical PPPoE safety patch. Its patch number0002 is already IKEv2; restoration by filename would conflict.

Pinned VPP plugin source establishes the limits:

- `pppoe.c:pppoe_init` owns both discovery0x8863 and session0x8864 EtherTypes. `linux-cp/lcp_interface.c:lcp_ethertype_enable` returns INVALID_REGISTRATION for a different existing owner. Global linux-cp EtherType registration cannot transparently coexist with the active PPPoE plugin.
- `pppoe.h:pppoe_main_t` has ONE `cp_if_index`; `pppoe_cp.c:pppoe_add_del_cp` overwrites it and enables the device-input feature without a CP readback API. `pppoe_cp_node.c` sends physical-side control to this singleton and CP-originated traffic by destination-MAC lookup. An unlearned broadcast PADI cannot select its WAN from that server lookup.
- `pppoe.h:pppoe_entry_key_t` uses MAC+sessionID, without parent/role/VLAN. `pppoe.c:vnet_pppoe_add_del_session` first needs a learned MAC→interface link. Two WANs contacting the same AC MAC can overwrite link ownership; repeated session IDs on different parents can alias. Current API has no explicit encapsulation parent or client/server role input. Per-session Go map keys alone cannot fix these VPP collisions.
- Native rewrite emits PPP IPv4 and IPv6 protocol values and input decapsulates both into the session interface. This is evidence of possible dual-family reuse, not proof of a working client. `pppoe_api.c` resolves add-session tables through ip4_main and leaves the argument is_ip6 unset; session creation stores one client IP/decap FIB. IPv6 table binding and link-local next-hop behavior must be checked separately. IPv6 RA/DHCPv6 are IP data, not LCP/IPV6CP: when native IP decapsulation consumes them, the present Linux ppp0 RA/dhcpcd observer might stop receiving them. A control delivery design must precede dual-stack acceptance.

### Configuration-only alternatives and their limits

Current physical-WAN address/default-route/MSS configuration cannot create PPP framing. Session-up/default-route status cannot promise NAT or forwarded traffic. Enabling LcpEthertypeEnable cannot override the plugin registration conflict. Disabling pppoe_plugin and globally punting both EtherTypes can let Linux negotiate, but removes the native server path and still leaves VPP LAN packets without PPPoE encapsulation. It is D, not an implemented alternative to A/B.

C is the concrete no-VPP-C datapath candidate: VPP LAN input→VPP firewall/NAT→plain-IP transit endpoint→kernel route→ppp0→exclusive raw-WAN transport, and reverse ingress must go back through VPP before reaching LAN. Kernel NAT must stay off; raw WAN must not leak plain IP or bypass VPP policy. A permanent VPP L2 cross-connect could carry discovery+session Ethernet to the client's LCP tap while pppd handles encapsulation, but coexistence isolation/feature ordering is only a source-supported hypothesis until private packets prove it. The historical discovery cross-connect does not establish the permanent dual-stack bridge/transit implementation.

C needs Go renderer/reconciler and reviewed kernel route/namespace provisioning: it is configuration using existing VPP APIs, not a configuration the current product already knows how to deploy. Dedicated Linux-NIC dialing is another transport variant, not permission to detach any shared/data/management NIC. Kernel forwarding and Linux routing become part of the product datapath, affecting operational policy, routing identity and upgrade/recovery; owner must accept that architectural tradeoff. Thus no complete same-appliance client+server/multi-WAN solution is already available through configuration alone under this task's existing boundaries.

## Recommendation and bounded implementation contract

Recommend **A first**, contingent on explicit approval of its narrower support scope and the exact exceptions below. It recovers the historical mechanism rather than recreating PPP discovery/authentication in VPP. It preserves VPP NAT/firewall forwarding and makes the single CP a deliberate resource. The full original PPPoE/IPv6 feature remains incomplete. If simultaneous server/client or multiple WANs is a release requirement, choose B instead; do not ship A with undisclosed restrictions. If owner declines all VPP C, C requires its own architectural/security approval and private proof; choosing D keeps unsupported disclosure and current work moving without a product dial/transit promise.

Phase A is one untagged client (MTU1492 or lower) on an exclusive parent with no static addresses/L2 assignments, owning its configured VRF. Fail semantic/agent validation with JSON pointers on second client, duplicate parent, any server CP/session configuration, unsupported IPv6 enabled mode, or foreign/unknown CP ownership. Default-route disabled must still allow explicitly routed IPv4 client packets. NAT44 ED is the first accepted NAT mode; other modes/ACL/Global Blocking must either be proven on the effective session interface or clearly rejected if selected, never silently bypassed. Pre-existing unrelated defaults/routes must survive.

A's proposed narrow C allowance is exactly: (1) late control/drop safety when CP missing, including safe teardown; (2) session dump reply message-base correction; (3) additive read-only CP endpoint readback sufficient for authoritative expected-owner checks. Existing CP setter semantics/ABI are preserved; no multiple CPs, new global EtherType ownership, broad plugin rewrite or installed-host replacement. Getter message names/IDs are deliberately not invented here; the binding/API owner derives them from an approved additive source contract, commits the contract before consumers and generates bindings normally. If source review shows those three changes insufficient for A's fail-closed requirements, stop that new implementation item and request a precise expanded design, not an inferred allowance.

The CP getter closes a production gap the historical feature-probe heuristic cannot fully prove: a feature enabled on a tap is not authoritative readback of cp_if_index. A unified globals-owner coordinator must hold the existing transaction exclusion, verify expected current CP and preserve unrelated feature/route state. Boot-scoped ownership records supplement actual readback; neither caller may override server ownership. No getter currently exists; this is a proposed C addition, not a historical test result. If an unknown CP belongs to another controller, fail before mutation.

Proposed lifecycle: validate+resolve pinned secret→claim/reserve parent/CP→stage private PPP files/unit→establish discovery cross-connect→spawn owned pppd→validate generation-bound AC/session identity→claim/create native session and sanitize it before addressing/up→set table/default/MSS/policy attachments→mark public forwarding-ready. Teardown revokes hook writers, withdraws only owned policy/routes/session effects, returns dialing transport as needed, stops unit and relinquishes CP only when no owned session/writer remains. Failed prepare/up/rollback must restore the prior configuration and observed ownership; empty down state never constitutes successful old-session cleanup. Process identity, bounded shutdown and late-writer fences from the published IPv6 candidate remain required; historical source is reconciled into current scheduler/contracts, not cherry-picked wholesale.

Keep configured logical WAN stable; expose negotiated session as operational state, not new config. Map NAT outside/output role, ingress+egress ACL, Global Blocking, uRPF and applicable counters to the effective session path. Test denying traffic before allowing it; a physical-parent attachment can miss native-session ingress. Unsupported selected policy must fail before dial. Interface-derived NAT pools must observe address changes; stale source translations cannot outlive wrong interface/session generations. Do not implicitly add new multi-WAN gateway handoff behavior.

Security allowance is separately bounded: private product PPP directory (for example /etc/ngfw/ppp), owned unit definitions under a restricted runtime subtree, per-unit private bind over /etc/ppp and validated NetworkNamespacePath for the exact owned LCP namespace. Agent writes only those directories; systemctl argv/unit names stay allowlisted and configured slots remain unable to supervise host units. Review the narrow writable paths/unit-link mechanism against ProtectSystem=strict, ProtectKernelTunables, NoNewPrivileges, current capabilities and pppd /dev/ppp needs. Prefer fixed packaged/runtime units; never make /etc/systemd/system or all /etc writable. New capabilities, master-key/socket changes, global sysctl/module/NIC changes are outside A and require another owner decision. Package dependencies and private namespace paths must be tested on a dedicated appliance image; installed tools on the lab are not packaging proof. Approval of this design is not authorization for shared-host changes.
