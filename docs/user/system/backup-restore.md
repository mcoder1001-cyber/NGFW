# Configuration backup, restore and appliance upgrades

Administrators use **System → Backup & Restore** to download an encrypted backup, restore into the candidate, schedule exports, apply templates and download support information. **System → Upgrade** drives the existing signed appliance image mechanism. Every mutation is audited. Operators and read-only users cannot invoke these endpoints.

Backups use a user passphrase of 12–1024 characters. Keep it separately: an incorrect passphrase or modified archive fails authentication before any candidate or secret is staged. Files named `ngfw-backup-<timestamp>.ngfwbackup` use format `NGFWBKP1`: a fixed header, random scrypt salt, random AES-256-GCM IV and authentication tag, followed by encrypted gzip JSON. The authenticated manifest carries schema version, revision, document SHA-256, creator and creation time. This is a versioned NGFW archive, not an age-compatible file. Format and schema major versions are checked; older minor documents are parsed through the current schema defaults. Compressed and expanded archives are bounded to 32 MiB. The archive includes the running document, up to 1000 revisions (default 100), the secret versions pinned by those revisions, and up to 10000 audit entries from the last 30 days. Audit exports are bounded; they are not a complete archival audit system.

Secret values exist only inside the passphrase-encrypted archive and are encrypted under the destination's local secret-store key when staged. Restore does not need the source device's master key. Restore never updates running directly and never activates restored credentials before commit. Upload with the passphrase, inspect the candidate diff, then use the normal validate/commit/confirmed-commit workflow. Discard releases the candidate and its staged version pins. Failed validation/application leaves live credentials unchanged; confirmed-commit promotion uses the staged pins. Sessions, API keys, MFA accounts and `app_user` rows are not restored. Local user definitions/roles from the current running document are preserved, and password hashes come from the existing account store (D-097/D-102).

Schedules are ordinary candidate configuration at `/management/backup`, committed through the pending-change bar. Set enabled, UTC cron, target, retention, revision count and a `password/<name>` passphrase reference. Cron has five fields (minute, hour, day of month, month, day of week); each supports `*`, `*/n` or one integer. Field bounds are validated. Day-of-month and day-of-week restrictions both match when both are specified. `0 2 * * *` means 02:00 UTC. Each due minute is durably claimed once across API processes. Recent outcomes survive restarts and are shown on the page.

Local exports write mode-0600 files to an absolute directory. SFTP requires host, username, a password/key reference, an absolute remote directory and pinned SHA-256 host key fingerprint (64 lowercase hex characters), with optional port. Transfers never invoke a shell. Local/SFTP retention deletes only regular files matching the generated NGFW backup naming pattern; unrelated files and symlinks are preserved. HTTPS performs a bounded TLS-verified PUT to the configured URL, without redirects, and optionally authenticates with a secret reference. It sends `x-ngfw-backup-filename` and `x-ngfw-backup-retention`; the HTTPS receiver must store separate objects and enforce retention. This API does not delete remote HTTPS objects.

Templates have a description, typed string/number/boolean parameters and an RFC 7386 merge patch. `${hostname}` as an entire JSON string is replaced by the typed parameter value; there is no expression evaluator or string substitution. Template definitions themselves are staged and committed. Applying a definition merges into the candidate and produces a preview diff. Unknown/missing parameters, control characters, prototype keys and inline credential keys are refused. Secret references may be used; passwords/PSKs/private keys belong in the secret store. Internally the validated template patch is stored as `patchJson` for a scalar schema/protobuf mirror; the templates API presents it as a JSON object.

Support downloads contain redacted running configuration, the last 1000 value-free audit summaries, agent Health (including the VPP version from binary API), Retrieve subsystem/interface counts, and a fixed read-only service/kernel/OS collector. Raw journals, process environments, secret-store values and password hashes are excluded. A final scan fails the export if credential keys, private-key material or password hashes are detected. A failed or unavailable collector fails the download.

Upgrade uploads stream raw `application/vnd.ngfw.update` data to the dedicated updates directory (maximum 8 GiB), independently of the 8 MiB default JSON limit. The filename header must be `ngfw-update-<major.minor.patch>.tar`; the server returns its own safe upload path. Stage that path, inspect inactive slot version, activate for the next boot, confirm a healthy trial or request rollback. Upload does not stage or boot anything. Status runs read-only; mutations execute dedicated fixed `ngfw-upgrade@{stage,activate,confirm,rollback}.service` instances through the agent, preserving its existing filesystem sandbox. The signed bundle/verifier/boot flags/watchdog remain owned by F-ab-upgrade. Consult [A/B appliance upgrades](../../install/ab-upgrade.md) before actual appliance use. Development tests never stage or activate this shared host.

REST equivalents: `POST /api/v1/actions/backup` with `{passphrase,revisions}`, `POST /api/v1/actions/restore` with `{passphrase,archive}` (base64), `GET/PUT /api/v1/config-templates/:name`, `POST /api/v1/config-templates/:name/apply` with `{parameters}`, `POST /api/v1/actions/support-bundle`, and `POST /api/v1/actions/upgrade` with an operation enum. Read schedule state from `GET /api/v1/state/backup`. Read candidate schedules at `/api/v1/config/candidate/management/backup`; stage edits with `PUT /api/v1/config/management/backup`. Commit/confirm/rollback use the existing configuration API. The equivalent appliance CLI is `ngfw-upgrade status --json`, `stage <bundle>`, `activate`, `confirm`, `rollback`; backup/restore/templates currently use the REST API rather than a separate appliance CLI wrapper.

Fleet provisioning, cloud object storage, HA synchronization, RESTCONF formats, complete account recovery and real upgrades of the development host are outside this feature. VMware boot/rollback/watchdog acceptance remains in F-ab-upgrade's laboratory acceptance record.
